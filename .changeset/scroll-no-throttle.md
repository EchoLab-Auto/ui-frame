**滚动时动画不再降速：去掉滚动节流，并优化渲染热路径**

画布循环曾在页面滚动期间**完全停止重绘**（为了修滚动卡顿），后改为降帧到 20fps。
两次都是同一个错误前提：把画布当成滚动的瓶颈。实测推翻了它——

- **独立长列表页 + 400×500@DPR2 的字符画满帧绘制**：滚动全程 60fps、零掉帧，
  帧间隔 p50/p90 都是 16.7ms；
- **同一页面完全不画**：也是 60fps / 零掉帧。

也就是说，画布绘制（3654 格的 `fillText`，单帧 median 1.1ms / p90 9.4ms）根本
不会拖累滚动。于是这一版把滚动节流整个去掉：**滚动时动画与静止同速**。

```ts
// 默认什么都不做——滚动不影响播放节奏
useArtRenderer({ ... })

// 只有自绘了特别重的内容才需要手动限速（0 = 滚动期间停绘）
useArtRenderer({ .../* */, scrollFps: 12 })
```

配套的两处改动：

1. **默认不再注册 `window` 的 capture 阶段 `scroll` 监听**。原先每个画布实例都会
   挂一个（只为了它不需要的节流），卸载时再摘掉。现在只有显式配置 `scrollFps`
   才注册。
2. **呼吸相位改用和角公式分解**。原来是逐格 `sin(ωt + phase)`，一帧几千次三角
   调用；用 `sin(ωt)·cos(phase) + cos(ωt)·sin(phase)` 展开后每帧只算一次
   `sin(ωt)`/`cos(ωt)`，逐格退化为两次乘法一次加法。数学上完全等价
   （Float32 相位存储误差 ~1e-7），有测试锁定等价性（容差 1e-4）。
3. **节流改用节拍器而不是「距上次多久」**。原来的判断是
   `now - lastDrawAt >= interval - 1`，在 rAF 抖动（16.7 / 33.4ms 交错）时
   33.4ms 刚好卡在 33.3ms 阈值边缘，一抖就少画一帧——实测把 30fps 的目标
   拖到 25fps。改成累计「下一次允许绘制的时刻」后，漏掉的拍子下一拍就补上，
   落后太多时重置节拍（不连画多帧追赶）。

实测（Chromium，391×489 画布，字符画蒙版，`idleFps: 30`）：

| 版本 | 静止 | 滚动中 |
| --- | --- | --- |
| 滚动完全停绘 | 33.4ms | 不绘制 |
| 滚动降到 20fps | 33.4ms | 40.1ms（25fps） |
| 去掉节流（阈值法） | 33.4ms | 39.4ms（25fps） |
| **去掉节流 + 节拍器** | 33.4ms | **33.2ms（30fps）** |

现在滚动与静止同速。

另外说明：在组件总览这类**同时渲染几十个霓虹/Neu 卡片**的页面上，滚动本身
仍会有掉帧，但那来自 `box-shadow` 的合成开销（profile 里 57% 时间在浏览器原生
光栅化），与画布无关——把画布搬进 Worker（`OffscreenCanvas`）后掉帧幅度不变，
可以佐证这一点。
