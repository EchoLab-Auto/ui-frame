# 文档分层与撰写规范

> 本文档说明 @echolab-auto/ui-frame 项目的文档组织结构，以及 Agent 在撰写或修改文档时应遵循的原则和规范。

---

## 一、文档目录结构

项目文档按读者对象分为两层，存放于 `document/` 目录，整体遵循 [ProDoc 文档标准](#四prodoc-参数区规范)：

```
document/
├── project.md               # 文档群图根入口
│
├── user/                    # 使用层 — "怎么用"（面向使用者）
│   ├── user.md                # 使用指南（教程式，按场景阅读）
│   ├── api.md                 # API 参考文档
│   ├── components.md          # 组件总览（分类说明、关键 props 与亮点）
│   ├── animation.md           # 动画效果（阴影模型、缓动、动效）
│   ├── interaction.md         # 交互效果（键盘、焦点、弹出层、反馈）
│   ├── agent-guide.md         # Agent 构建指南（组件目录 + 模式 + 决策指南）
│   └── components/            # 组件详情文档（每组件一篇）
│       ├── button.md            # NeumorphismButton 详解
│       ├── switch.md            # NeumorphismSwitch 详解
│       ├── checkbox.md          # NeumorphismCheckbox 详解
│       ├── radio.md             # NeumorphismRadio 详解
│       ├── input.md             # NeumorphismInput 详解
│       ├── textarea.md          # NeumorphismTextarea 详解
│       ├── select.md            # NeumorphismSelect 详解
│       ├── art.md               # NeumorphismArt 详解
│       └── ascii-art.md         # NeumorphismAsciiArt 详解
│
└── develop/                 # 开发层 — "该怎么写"（面向开发者）
    ├── develop.md             # 开发入口索引与快速参考
    ├── design-philosophy.md   # 设计理念
    ├── design-patterns.md     # 设计模式
    ├── develop-pipeline.md    # 开发验证流程
    ├── documentation-guide.md # 本文档
    ├── readme-specification.md# 项目 README 内容规范
    ├── ci-pipeline.md         # CI 流程设计与验证链路
    └── ci-design.md           # CI/CD 架构设计说明
```

## 二、各层文档的定位

### `document/user/` — 使用层

**读者**：使用本库构建应用的外部开发者（含构建 UI 的 Agent）

**目的**：回答"怎么用"和"有什么"的问题

**内容特征**：

- 按读者对象拆分为 API 文档、用户指南和 Agent 构建指南三份
- 所有可被外部使用的模块必须有文档覆盖
- 类型定义完整，示例代码可直接复制运行

**文档分工**：

| 文档             | 面向读者                 | 内容风格                   | 查询方式       |
| ---------------- | ------------------------ | -------------------------- | -------------- |
| `api.md`         | 需要精确接口信息的开发者 | 参考手册式，表格化、类型化 | 按模块名检索   |
| `user.md`        | 需要学习如何使用的开发者 | 教程式，场景驱动           | 按使用场景阅读 |
| `components.md`  | 需要挑选组件的开发者     | 分类速览式，表格 + 亮点    | 按功能分类检索 |
| `animation.md`   | 需要理解动效的开发者     | 机制说明式，规律 + 示例    | 按动画主题阅读 |
| `interaction.md` | 需要理解交互的开发者     | 机制说明式，约定 + 行为表  | 按交互主题阅读 |
| `agent-guide.md` | 使用本库构建 UI 的 Agent | 速查式，组件目录 + 决策表  | 按任务类型检索 |

**拆分原则**：

- API 文档聚焦"这是什么" — 精确描述每个导出模块的签名、参数、返回值、类型
- 用户指南聚焦"怎么做" — 以使用场景组织，提供完整的可运行示例
- 两者内容可以交叉引用，但不应重复详述同一内容

---

### `document/develop/` — 开发层

**读者**：参与本项目开发的 Agent 或开发者

**目的**：在编码之前建立共识，回答"该怎么写"的问题

**内容特征**：

- 不写具体 API，只写设计原则和约束规则
- 使用祈使语气，条目清晰可检查
- 包含流程图、检查清单等可执行的结构
- 变更频率低，是项目的"宪法"

**现有文档职责**：

- `develop.md` — 开发入口索引与各规范快速参考
- `design-philosophy.md` — 六条核心设计原则，所有组件实现的判断依据
- `design-patterns.md` — 源码中使用的具体设计模式
- `develop-pipeline.md` — 从编码到提交到 CI 的完整验证流程
- `documentation-guide.md` — 文档本身的组织结构与撰写规范
- `readme-specification.md` — 项目根目录 README 的内容结构与撰写标准
- `ci-pipeline.md` — CI 流程设计原则与验证链路
- `ci-design.md` — CI/CD 架构设计说明（面向需要修改 CI 的开发者）

## 三、文档撰写规范

### 3.1 通用格式

- 使用 Markdown 格式，一级标题为文档名，二级标题用 `##`，三级用 `###`
- 同级标题之间用 `---` 分隔
- 代码块标注语言（`ts`、`vue`、`scss`、`bash`）
- 中英文混排时，英文与中文之间留一个空格

### 3.2 API 文档撰写规范

**模块组织**：按功能领域分组（基础输入、表单、数据展示、导航、反馈、布局、扩展）

**每个组件/函数的条目必须包含**：

1. **导入语句** — `import { Xxx } from '@echolab-auto/ui-frame'`
2. **类型导入**（如有）— `import type { XxxProps } from '@echolab-auto/ui-frame'`
3. **Props / 参数表格** — 列：名称、类型、默认值、说明
4. **事件表格**（如有）— 列：事件名、参数、说明
5. **插槽表格**（如有）— 列：名称、说明、作用域参数
6. **类型定义**（如有）— 使用 TypeScript interface 展示数据结构
7. **简短示例** — 展示最常见用法，不超过 10 行

**禁止**：

- 不堆砌组件描述性文字，用表格代替大段 prose
- 不重复已在源码类型中表达的信息
- 不写内部实现细节（如 composable 内部状态名）

### 3.3 用户指南撰写规范

**内容组织**：按使用场景而非按模块名组织

**每个场景必须包含**：

1. **场景说明** — 一句话说明解决什么问题
2. **完整可运行示例** — 包含 `<script setup>`、`<template>`、`<style>`
3. **关键代码注释** — 标注需要注意的点
4. **与相关场景的交叉引用** — 如"参见 [表单验证](#表单验证)"

**禁止**：

- 不罗列 API（这是 API 文档的职责）
- 不提供不可运行的代码片段
- 不深入源码实现原理

### 3.4 CI 文档撰写规范

**文件位置**：`document/develop/ci-design.md`

**读者**：需要理解或修改 GitHub Actions CI/CD 的开发者

**内容组织**：按工作流逐一说明，每个工作流必须包含：

1. **触发条件** — `on:` 的完整配置，包括分支、事件类型、手动触发
2. **任务流水线** — 按执行顺序列出每个步骤的命令和说明
3. **设计要点** — 并发控制、权限配置、产物复用策略、环境变量说明
4. **故障排查** — 常见失败场景的症状、根因与修复方法

**格式要求**：

- 使用表格展示步骤列表（步骤名 | 命令 | 说明）
- 使用 ASCII/文本流程图展示工作流之间的触发关系
- 环境变量和 Secrets 必须说明用途，不暴露具体值
- 产物校验清单必须逐项列出，不可省略

**禁止**：

- 不写与 CI 无关的内容（如组件使用教程、API 说明）
- 不假设读者熟悉 GitHub Actions 基础概念，关键配置应简要解释
- 不遗漏 `workflow_run` 等触发依赖关系的说明

### 3.5 文档维护原则

- **新增可被外部使用的模块** → 必须同步更新 API 文档
- **新增使用场景** → 必须同步更新用户指南
- **修改接口签名** → 必须同步更新两份文档
- **新增/修改 CI 工作流** → 必须同步更新 `ci-design.md`
- **修改 CI 环境配置**（Node 版本、npm 版本、环境变量） → 必须同步更新 `ci-design.md`
- **纯内部重构不触及外部接口** → 无需更新文档

## 四、ProDoc 参数区规范

本目录是一个 **ProDoc 文档群**：`document/` 下的每个 `.md` 文件是文档图上的一个框，可用 DocRenderer（`echo-prodoc view ./document`）渲染为可交互图画布。

**新增或修改文档时必须遵守**：

1. **参数区必备**：文件第 0 字节起是两个 `---` 行夹住的框架参数区，正文渲染时被完全剥离
2. **必填字段**：`id`（目录内唯一）、`title`、`x` / `y`（画布坐标，新增文档时手工指定，与同组已有框保持网格对齐）
3. **可选字段**：`group`（`使用` 或 `开发`，决定画布上的分组区域）；`link`（`["目标id | 标签"]`，声明指向其他文档的导航连线）
4. **导航一致性**：文档正文末尾的「深入/参见」相对链接应与参数区 `link` 声明的连线保持一致
5. 完整规则（字段类型、容错、分层布局、分组区域）以 DocRenderer 仓库的 `document/develop/prodoc-rule/prodoc.md` 为权威定义
